# MyPace 제품 및 기술 설계서

## 1. 문서 목적

이 문서는 MyPace MVP의 제품 범위, 화면 디자인, 기능, 데이터 구조, 기술 구조와 개발 순서를 정의한다. 실제 코드와 환경변수 파일을 만들기 전에 구현 기준을 합의하기 위한 문서다.

각 기능이 연결되는 React 파일, FastAPI 파일, API, 데이터 테이블과 담당 Task는 `docs/mypace-implementation-plan.md`의 **Feature-to-File Traceability** 표를 기준으로 한다.

## 2. 프로젝트 개요

### 서비스명

- 영문: MyPace
- 한글: 마이페이스
- 슬로건: 내 수입에 맞춰, 소비도 마이페이스

### 한 줄 소개

수입과 소비 흐름을 분석해 나만의 지출 속도와 맞춤 예산을 제안하는 AI 개인 재무관리 플랫폼.

### 해결하려는 문제

- 월수입은 알고 있지만 얼마까지 사용해도 되는지 판단하기 어렵다.
- 예상 수입과 실제 입금액이 다르면 기존 예산이 현실과 맞지 않게 된다.
- 소비 기록만 보여주는 가계부는 다음 행동을 결정하기 어렵다.
- 직장인과 대학생은 수입 구조가 다르지만 공통된 수입·지출 관리 기능이 필요하다.

### 핵심 가치

1. 사용자의 예상 수입을 기준으로 추천 예산을 먼저 제시한다.
2. 실제 수입이 확정되면 남은 예산과 지출 가능 금액을 다시 계산한다.
3. 소비 변화를 수치와 쉬운 문장으로 설명한다.
4. 투자 권유보다 올바른 지출과 생활비 관리에 집중한다.

## 3. 개발 조건

- 개인 개발 프로젝트
- 개발 기간: 2~4주
- 시연 가능한 준실서비스 수준의 MVP
- 실제 금융기관 연동 대신 합성 거래 데이터 사용
- 실제 계좌번호, 카드번호 등 민감 금융정보 저장 금지
- AI가 실패해도 핵심 재무관리 기능은 정상 작동

## 4. 핵심 사용자

### 직장인

- 월 실수령액 직접 입력
- 급여 외 부업·기타 수입 추가 가능
- 고정지출과 생활비 균형 강조
- 전월 대비 소비와 카테고리별 예산 소진율 강조

### 대학생

- 아르바이트 예상 수입과 실제 입금액 입력
- 용돈·장학금·기타 수입 추가 가능
- 수입 변동성과 남은 생활비 강조
- 이전 기간 대비 지출률 변화 강조

### 공통 구조

사용자 유형별 애플리케이션을 별도로 만들지 않는다. 데이터 구조와 기능은 공유하며, 초기 설정 질문과 대시보드에서 강조하는 정보만 다르게 제공한다.

## 5. MVP 사용자 흐름

```text
회원가입 또는 카카오 로그인
  → 사용자 유형 선택
  → 월 예상 수입과 수입원 입력
  → 고정지출 및 기본 소비 정보 입력
  → MyPace 추천 예산 확인
  → 사용자가 카테고리별 예산 조정
  → 합성 거래 데이터 불러오기 또는 직접 거래 입력
  → 대시보드에서 예산 사용률과 소비 변화 확인
  → 실제 수입 입금 후 분석 보정
  → 월간 리포트 확인 및 PDF 다운로드
```

## 6. MVP 기능 범위

### 6.1 인증과 프로필

- 이메일 회원가입 및 로그인
- 이메일 인증
- 카카오 OAuth 로그인
- 로그아웃
- 직장인·대학생 유형 선택
- 표시 이름 및 기본 프로필 관리
- Supabase Auth 사용

### 6.2 수입 관리

- 월 예상 실수령액 입력
- 실제 입금액 입력
- 급여, 아르바이트, 부업, 용돈, 장학금, 기타 수입원 관리
- 반복 수입과 일회성 수입 구분
- 예상액과 실제액 차이 표시
- 실제액 확정 후 예산 자동 재계산 제안

### 6.3 금융계정과 거래 관리

- 은행 계좌, 카드, 현금 계정의 시연용 등록
- 실제 금융기관 인증정보 저장 금지
- 합성 거래 데이터 불러오기
- 거래내역 직접 추가·수정·삭제
- CSV 업로드는 시간 여유가 있을 때 포함
- 거래 카테고리 수정

### 6.4 예산 관리

- 예상 수입과 기존 소비를 바탕으로 초기 추천 예산 생성
- 필수지출, 저축, 선택지출 순서로 배분
- 카테고리별 추천 이유 표시
- 사용자가 추천 예산 직접 조정
- 예산 총액이 기준 수입을 넘으면 경고
- 실제 수입 감소 시 남은 기간의 일일 사용 가능 금액 재계산

### 6.5 소비 분석

- 이번 달 총지출
- 수입 대비 지출률
- 예산 사용률
- 남은 생활비
- 남은 기간 하루 사용 가능 금액
- 전월 대비 소비 증감률
- 최근 3개월 평균 대비 변화
- 카테고리별 소비 비중과 증감
- 직장인·대학생 유형에 따른 강조 지표 변경

### 6.6 제한형 AI 도움 기능

AI는 핵심 계산을 수행하지 않고 FastAPI가 계산한 결과를 설명한다.

- 소비 패턴 요약
- 예산 추천 이유 설명
- 월간 리포트 문장 생성
- 정해진 재무 데이터 범위 안의 간단한 질문 답변
- 투자 종목 추천, 수익률 예측, 대출 권유 금지
- 거래 추가·삭제 등 데이터 변경 명령 금지
- 범용 자유 대화형 챗봇으로 확장하지 않음

예시:

> 이번 달 카페 지출이 지난달 같은 기간보다 27% 증가했습니다.

> 실제 수입이 예상보다 50,000원 적어 여가 예산을 30,000원 낮추는 것을 추천합니다.

### 6.7 월간 리포트

- 월수입, 총지출, 저축 가능액 요약
- 예산 대비 실제 소비 비교
- 주요 소비 변화 설명
- 다음 달 권장 예산
- PDF 생성 및 다운로드

## 8. 디자인 방향

### 디자인 콘셉트

- 밝은 아이보리 계열 배경
- 신뢰감을 주는 딥블루 중심색
- 안정적인 소비 상태를 나타내는 민트 포인트
- 은행 앱보다 부드럽고 일반 가계부보다 전문적인 분위기
- 과도한 카드, 그림자, 장식 사용 금지
- 숫자와 사용자의 다음 행동이 가장 먼저 보이는 구성

### 디자인 키워드

`신뢰감`, `안정감`, `명료함`, `개인화`, `부담 없는 금융`

### 색상 역할

| 역할 | 방향 |
|---|---|
| 페이지 배경 | 따뜻한 아이보리 |
| 기본 텍스트 | 짙은 네이비 |
| 주요 버튼·선택 상태 | 딥블루 |
| 정상·절약·여유 상태 | 민트 |
| 주의 상태 | 앰버 |
| 초과·오류 상태 | 낮은 채도의 레드 |

### UI 원칙

- 금액은 천 단위 구분과 `원` 단위를 항상 표시한다.
- 색상만으로 정상·주의·초과 상태를 구분하지 않고 문구나 아이콘을 함께 사용한다.
- 차트에는 제목, 기간, 단위와 핵심 값을 표시한다.
- AI 설명에는 계산 근거와 비교 기간을 함께 보여준다.
- 주요 버튼은 한 화면에 하나의 우선 행동만 강조한다.

## 9. 화면 전략

### 이번 MVP: 데스크톱 우선 반응형 웹

먼저 데스크톱 웹사이트를 완성한다. CSS는 유동 너비, Grid/Flex 재배치, 넘침 방지를 적용해 화면 폭이 줄어도 레이아웃이 깨지지 않게 작성한다. 하지만 모바일 전용 사용자 경험은 이번 단계의 완료 조건에 포함하지 않는다.

```text
1단계: 데스크톱 웹 기능과 화면 완성
2단계: 브라우저 폭 축소 시 깨짐 방지 및 기본 재배치
3단계: 데스크톱 기준 통합 테스트와 시연 완성
4단계: 후속 작업에서 모바일 전용 UI 구현
```

### 후속 모바일 웹

모바일 단계에서는 같은 React 코드베이스와 API를 재사용하며 다음 UI만 별도로 구현한다.

- 사이드바를 하단 내비게이션으로 변경
- 거래 테이블을 카드 목록으로 변경
- 예산 편집 패널을 전체 화면 또는 바텀시트로 변경
- 주요 수치와 행동 중심으로 대시보드 정보 축약

### 권장 화면 기준

- 주 개발·검수 기준: 1280px 이상 데스크톱
- 기본 대응: 768~1279px 노트북·태블릿 폭에서 깨짐 방지
- 767px 이하: 내용 접근은 가능하게 유지하되 모바일 UX 완성은 후속 범위

## 11. 프런트엔드 구조

### 확정 기술

- React
- TypeScript
- Vite
- Chart.js

React Router, 서버 상태 관리 라이브러리와 UI 라이브러리는 프로젝트 초기화 전에 최종 결정한다.

```text
frontend/
├── public/
├── src/
│   ├── api/                 # FastAPI 요청 함수
│   ├── assets/              # 로고와 정적 리소스
│   ├── components/
│   │   ├── common/          # 버튼, 입력, 카드, 차트
│   │   ├── desktop/         # 데스크톱 사이드바, 거래 표
│   │   └── mobile/          # 후속 모바일 구현용
│   ├── features/
│   │   ├── auth/
│   │   ├── onboarding/
│   │   ├── income/
│   │   ├── transactions/
│   │   ├── budgets/
│   │   ├── analytics/
│   │   └── reports/
│   ├── layouts/
│   ├── pages/
│   ├── styles/
│   ├── types/
│   ├── App.tsx
│   └── main.tsx
├── .env.example
├── package.json
└── vite.config.ts
```

### 프런트엔드 분리 원칙

- API 호출과 화면 코드를 분리한다.
- 데이터 계산을 React 컴포넌트에서 중복 구현하지 않는다.
- 수치 계산 결과는 FastAPI 응답을 사용한다.
- 공통 컴포넌트는 화면 크기와 무관하게 재사용한다.
- `mobile` 폴더는 후속 구현 전까지 비워두거나 생성하지 않아도 된다.

## 12. 백엔드 구조

### 확정 기술

- FastAPI
- Pydantic
- SQLAlchemy 2.0
- Alembic
- Supabase PostgreSQL

```text
backend/
├── app/
│   ├── main.py
│   ├── core/                # 설정, 보안, 예외 처리
│   ├── models/              # SQLAlchemy 모델
│   ├── schemas/             # Pydantic 요청·응답
│   ├── routers/             # HTTP 요청과 응답
│   ├── services/            # 예산·분석 비즈니스 로직
│   ├── repositories/        # 데이터베이스 접근
│   ├── dependencies.py      # DB와 현재 사용자 주입
│   └── utils/
├── migrations/
├── tests/
├── .env.example
├── alembic.ini
└── requirements.txt
```

### 계층 책임

- Router: 요청을 받고 Schema로 검증한 뒤 응답한다.
- Service: 예산 추천, 수입 보정, 소비 분석 규칙을 수행한다.
- Repository: Supabase PostgreSQL 조회와 저장만 담당한다.
- Schema: API 입력과 출력 형식을 정의한다.
- Dependency: DB 세션과 인증된 사용자를 제공한다.

## 13. 전체 시스템 구조

```text
React 데스크톱 웹
  ├─ Supabase Auth: 이메일·카카오 로그인
  └─ Supabase Access Token
             ↓
FastAPI
  ├─ JWT 검증
  ├─ 사용자 소유권 검사
  ├─ 예산 계산
  ├─ 소비 분석
  ├─ PDF 생성
  └─ 제한형 AI 설명 요청
             ↓
Supabase PostgreSQL
  └─ RLS를 통한 사용자별 행 보호
```

## 14. Supabase 데이터 모델

모든 사용자 소유 데이터에는 `user_id`가 있어야 한다.

| 테이블 | 목적 | 주요 필드 |
|---|---|---|
| `profiles` | 사용자 설정 | user_id, display_name, user_type |
| `income_sources` | 수입원 | id, user_id, name, type, expected_amount |
| `income_entries` | 월별 수입 | id, user_id, source_id, period, expected_amount, actual_amount |
| `financial_accounts` | 시연용 계정 | id, user_id, name, account_type, provider_name |
| `categories` | 거래 분류 | id, user_id, name, kind |
| `transactions` | 수입·지출 내역 | id, user_id, account_id, category_id, amount, occurred_at |
| `budgets` | 월별 예산 | id, user_id, period, base_income, status |
| `budget_items` | 카테고리 예산 | id, budget_id, category_id, recommended_amount, adjusted_amount |
| `ai_insights` | 생성된 설명 | id, user_id, period, insight_type, evidence, content |
| `monthly_reports` | 월간 리포트 | id, user_id, period, summary, pdf_path |

### RLS 원칙

- 새 테이블 자동 RLS 활성화를 사용한다.
- 각 테이블에 SELECT, INSERT, UPDATE, DELETE 정책을 명시한다.
- 사용자는 자신의 `user_id` 행만 접근할 수 있다.
- FastAPI에서도 토큰의 사용자 ID로 소유권을 다시 검사한다.
- secret 또는 service-role 키를 React에 넣지 않는다.

## 15. 예산 추천 규칙

### 이중 수입 구조

- 예상 수입: 월초 추천 예산 생성에 사용
- 실제 수입: 입금 후 실제 분석과 남은 예산 보정에 사용

### 실제 수입이 예상보다 적을 때

1. 이미 발생한 지출은 변경하지 않는다.
2. 남은 필수지출을 먼저 보호한다.
3. 저축 목표는 사용자가 조정할 수 있게 제안한다.
4. 선택지출 예산을 우선 축소한다.
5. 남은 기간의 일일 사용 가능 금액을 다시 계산한다.
6. 변경 전·후 예산과 이유를 사용자에게 보여준다.

### 기본 계산식

```text
지출률 = 현재까지 지출 ÷ 실제 수입 × 100
예산 사용률 = 현재까지 지출 ÷ 확정 예산 × 100
남은 생활비 = 확정 예산 - 현재까지 지출
일일 사용 가능 금액 = 남은 생활비 ÷ 남은 일수
```

AI는 이 계산 결과를 변경하지 않고 설명만 한다.

## 17. 보안과 개인정보

- 환경변수 실제값은 `backend/.env`에만 저장한다.
- `.env`는 Git에 커밋하지 않는다.
- 저장소에는 키 이름만 있는 `.env.example`을 둔다.
- Supabase secret/service-role 키는 프런트엔드에 노출하지 않는다.
- 실제 계좌번호, 카드번호, 주민등록번호를 저장하지 않는다.
- AI에는 거래 원문 전체 대신 계산에 필요한 최소 정보만 전달한다.
- 로그에 토큰, 비밀번호, 연결 문자열과 금융 식별정보를 기록하지 않는다.
- 월간 PDF는 사용자별 비공개 경로와 만료되는 다운로드 주소를 사용한다.

## 19. 시연 시나리오

### 직장인

1. 예상 급여와 부업 수입을 입력한다.
2. MyPace 추천 예산을 확인하고 여가비를 조정한다.
3. 합성 거래내역을 불러온다.
4. 실제 급여가 예상보다 적게 입금된 상황을 반영한다.
5. 줄어든 선택지출 예산과 일일 사용 가능 금액을 확인한다.
6. 월간 리포트를 다운로드한다.

### 대학생

1. 아르바이트 예상 수입과 용돈을 입력한다.
2. 실제 아르바이트 임금의 차이를 반영한다.
3. 남은 생활비와 지출률 변화를 확인한다.
4. 카페 지출 증가 인사이트를 확인한다.
5. 다음 달 추천 예산을 검토한다.

## 20. MVP 완료 기준

- 회원가입 또는 카카오 로그인부터 대시보드 진입까지 완료할 수 있다.
- 예상 수입으로 추천 예산을 만들고 사용자가 수정할 수 있다.
- 실제 수입 입력 후 예산과 분석이 보정된다.
- 거래내역을 추가하고 카테고리를 변경할 수 있다.
- 월별·카테고리별 소비 그래프가 계산 결과와 일치한다.
- 다른 사용자의 데이터에 접근할 수 없다.
- AI가 실패해도 인증, 수입, 거래, 예산과 분석이 작동한다.
- 데스크톱 브라우저에서 전체 시연을 완료할 수 있다.
- 화면 폭이 줄어도 내용이 겹치거나 잘리지 않는다.
- 모바일 전용 UI는 후속 범위임을 문서와 발표에서 명시한다.
